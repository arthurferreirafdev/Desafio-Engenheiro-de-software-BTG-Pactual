# PROMPT — Sistema de Processamento de Pedidos (Desafio BTG Pactual)

Implemente, de forma completa e funcional, o sistema descrito em `problem.md` seguindo a
arquitetura proposta em `doc/` (diagrama de arquitetura + DER). A solução deve usar
**PostgreSQL** e **RabbitMQ**, ser construída em **.NET 8 (C#)**, seguir **arquitetura DDD
(Domain-Driven Design)** em camadas e respeitar os **princípios SOLID**. A aplicação deve ser
entregue rodando via Docker, com um único `docker-compose.yml` que suba todos os serviços.

---

## 1. Contexto e escopo

- Escopo do negócio: **processar pedidos e gerar relatórios**.
- Um cliente externo (`External Client`) publica mensagens de pedidos em uma fila RabbitMQ.
- O serviço (`Service/server`) consome essas mensagens, persiste os dados no PostgreSQL e
  expõe uma **API REST** consumida pelo front-end/clientes.
- Consultas obrigatórias:
  1. Valor total de um pedido.
  2. Quantidade de pedidos por cliente.
  3. Lista de pedidos realizados por cliente.

## 2. Stack tecnológica

| Camada           | Tecnologia                                             |
|------------------|--------------------------------------------------------|
| Runtime          | .NET 8 (LTS), C# 12                                    |
| API              | ASP.NET Core (Minimal APIs ou Controllers) + Swagger/OpenAPI |
| ORM              | EF Core 8 + Npgsql (escrita); queries de leitura via LINQ ou Dapper |
| Mensageria       | RabbitMQ.Client 6.8+ (consumer hosted service)          |
| Banco de dados   | PostgreSQL 16                                           |
| Testes           | xUnit, NSubstitute (ou Moq), Testcontainers, WebApplicationFactory |
| Ambiente         | Docker / docker compose (API + PostgreSQL + RabbitMQ)   |
| Observabilidade  | Logs estruturados (Serilog), HealthChecks               |

## 3. Arquitetura da solução

Conforme `doc/diagrama_arquitetura.excalidraw`, o fluxo é:

```
External Client ──publica──> RabbitMQ ──consome──> Service/server ──grava/lê──> PostgreSQL
                                                   ▲
Client/frontend ──────────── HTTP REST ────────────┘
```

- **Um único serviço implantável** hospeda, no mesmo processo: a API REST e o consumer
  RabbitMQ (implementado como `BackgroundService`/`IHostedService`).
- O serviço não deve perder mensagens: ack manual somente após persistência com sucesso.
- A leitura (queries da API) e a escrita (consumer) podem usar modelos separados
  (CQRS leve): o mesmo banco, com caminhos distintos no código.

## 4. Estrutura de pastas (DDD em 4 camadas + SOLID)

```
src/
  Btg.Orders.Domain/            # Camada de domínio (sem dependências externas)
  Btg.Orders.Application/       # Casos de uso, DTOs, ports (interfaces)
  Btg.Orders.Infrastructure/    # EF Core, repositórios, RabbitMQ, migrations
  Btg.Orders.Api/               # Host: endpoints REST, DI, hosted services
tests/
  Btg.Orders.UnitTests/         # Testes de domínio e aplicação
  Btg.Orders.IntegrationTests/  # Testes end-to-end (Testcontainers)
```

Responsabilidades por camada:

- **Domain**: entidades, agregados, value objects, invariantes, interfaces de repositório,
  eventos e serviços de domínio. **Não referencia** nenhuma outra camada.
- **Application**: casos de uso (handlers), orquestração, contratos (DTOs de entrada/saída),
  definição de *ports* (ex.: `IPedidoRepository`, `IUnitOfWork`, `IPedidoQueryService`,
  `IMessageConsumer`). Depende apenas do Domain.
- **Infrastructure**: implementações dos ports — `PedidoRepository` (EF Core),
  `PedidoQueryService`, consumer RabbitMQ, `DbContext`, migrations, resiliência.
- **Api**: composition root (injeção de dependência), endpoints REST, Swagger, health
  checks, configuração, hosted services.

Aplicação prática do **SOLID**:

- **S** — cada classe com uma única responsabilidade (ex.: consumer apenas recebe/valida e
  delega ao handler; cálculo de total fica no domínio).
- **O** — novas fontes/mensagens ou queries sem alterar código fechado: estenda via novas
  implementações de interfaces registadas no DI.
- **L** — implementações de repositórios/queries substituíveis sem quebrar contratos.
- **I** — interfaces pequenas e coesas (`IPedidoRepository`, `IProdutoRepository`,
  `IClienteQueryService`), nada de "interface-Deus".
- **D** — Application e Domain dependem de abstrações; Infrastructure implementa; a Api é o
  único ponto que conhece implementações concretas.

## 5. Modelo de domínio (tático)

Agregado raiz `Pedido`:

- `Pedido` (aggregate root): `CodigoPedido` (identidade), `CodigoCliente`, `CriadoEm`,
  coleção de `ItemPedido`.
- `ItemPedido`: `CodigoProduto`, `Quantidade`, `Preco`.
- `Produto` (entidade de suporte/catalogação): `CodigoProduto`, `Nome`, `Preco`.
- Value Objects: `Preco` (decimal > 0) e `Quantidade` (int > 0) com validação no construtor.

Invariantes (lançar exceção de domínio/`Result`):

- `quantidade` de item deve ser maior que zero.
- `preco` de item deve ser maior ou igual a zero (representação em dinheiro, nunca
  `double`; usar `decimal`).
- Pedido sem itens não deve ser persistido (mensagem com `itens` vazio → rejeitar, log,
  ack e descartar; não reprocessar infinitamente).
- `codigoPedido` e `codigoCliente` devem ser positivos.

## 6. Modelagem de dados (conforme `doc/DER.drawio`, com ajustes operacionais)

```sql
CREATE TABLE produto (
    codigo_produto INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nome           VARCHAR(200) NOT NULL,
    preco          NUMERIC(10,2) NOT NULL,
    criado_em      TIMESTAMP NOT NULL DEFAULT now(),
    CONSTRAINT uq_produto_nome UNIQUE (nome)
);

CREATE TABLE pedido (
    codigo_pedido  INT PRIMARY KEY,          -- vem da mensagem (idempotência natural)
    codigo_cliente INT NOT NULL,
    criado_em      TIMESTAMP NOT NULL DEFAULT now()
);
CREATE INDEX ix_pedido_cliente ON pedido (codigo_cliente);

CREATE TABLE item_pedido (
    codigo_pedido  INT NOT NULL REFERENCES pedido (codigo_pedido),
    codigo_produto INT NOT NULL REFERENCES produto (codigo_produto),
    codigo_cliente INT NOT NULL,
    preco          NUMERIC(10,2) NOT NULL,
    quantidade     INT NOT NULL,
    PRIMARY KEY (codigo_pedido, codigo_produto),
    CONSTRAINT ck_item_quantidade CHECK (quantidade > 0),
    CONSTRAINT ck_item_preco CHECK (preco >= 0)
);
```

Observações:

- O DER mantém `codigo_cliente` como coluna em `pedido` e `item_pedido` (não existe tabela
  cliente) — preserve esse desenho; se desejar normalizar, documente o desvio.
- A mensagem identifica produtos por **nome** (`"produto": "lápis"`): o consumer deve fazer
  *find-or-create* de `produto` por nome normalizado (trim + case-insensitive) e usar o
  `codigo_produto` gerado nos itens.
- Se o mesmo produto aparecer duas vezes na mesma mensagem, consolidar em um único item
  (somar quantidade) — a PK composta exigiria isso.
- Valor total do pedido é sempre **derivado**: `SUM(quantidade * preco)`. Nunca armazenar.

## 7. Contrato da mensagem (RabbitMQ)

Fila de entrada (exatamente como no `problem.md`):

```json
{
  "codigoPedido": 1001,
  "codigoCliente": 1,
  "itens": [
    { "produto": "lápis",   "quantidade": 100, "preco": 1.10 },
    { "produto": "caderno", "quantidade": 10, "preco": 1.00 }
  ]
}
```

Topologia do broker (declarada pela aplicação ao iniciar, de forma idempotente):

- Exchange: `pedidos.exchange` (direct)
- Queue principal: `pedidos.queue` (durable)
- Routing key: `pedido.criado`
- DLX: `pedidos.dlx` → `pedidos.dlq` (mensagens inválidas ou que excedem retentativas)

Regras do consumer:

- Desserializar JSON com `System.Text.Json` (cultura invariant, tratar vírgula/ponto com
  `CultureInfo.InvariantCulture`).
- **Idempotência**: mensagem reenviada com o mesmo `codigoPedido` não pode duplicar dados.
  Usar `INSERT ... ON CONFLICT (codigo_pedido) DO NOTHING` (ou verificar existência) e,
  se já existir, registrar log e fazer **ack** normalmente.
- Persistência transacional: pedido + produtos + itens em uma única transação
  (`IUnitOfWork`); ack somente após commit.
- Em caso de erro transitório (ex.: banco indisponível): **nack sem requeue** confiando na
  DLX + retry com backoff, ou requeue controlado com limite de tentativas (máx. 3) via
  header `x-death`/contador de retry.
- Mensagem malformada (JSON inválido / viola invariantes): log, publicar na DLQ para
  análise, ack.
- `Prefetch` = 10; consumer com log de início/fim e graceful shutdown.
- Publicar a mensagem na transação OUTBOX é opcional; documentar se adotar algo além do
  fluxo direto.

## 8. API REST (contratos)

Base: `/api`. Respostas em JSON, `ProblemDetails` (RFC 7807) para erros, 404 quando o
recurso não existir, 400 para validação.

1. **Valor total do pedido**

```
GET /api/pedidos/{codigoPedido}/total
200 -> { "codigoPedido": 1001, "codigoCliente": 1, "valorTotal": 120.00 }
404 -> pedido não encontrado
```

2. **Quantidade de pedidos por cliente**

```
GET /api/clientes/{codigoCliente}/pedidos/quantidade
200 -> { "codigoCliente": 1, "quantidadePedidos": 2 }
```
(Cliente sem pedidos retorna `quantidadePedidos: 0`, HTTP 200.)

3. **Lista de pedidos por cliente** (com paginação)

```
GET /api/clientes/{codigoCliente}/pedidos?page=1&size=10
200 -> {
  "codigoCliente": 1,
  "pagina": 1,
  "tamanho": 10,
  "totalPedidos": 2,
  "pedidos": [
    { "codigoPedido": 1001, "criadoEm": "2026-11-09T10:00:00Z",
      "valorTotal": 120.00, "quantidadeItens": 2 }
  ]
}
```

Requisitos transversais da API:

- Swagger/OpenAPI habilitado (acessível em `/swagger`).
- Health checks: `/health/live` (processo) e `/health/ready` (PostgreSQL + RabbitMQ) —
  packages `AspNetCore.HealthChecks.NpgSql` e `AspNetCore.HealthChecks.Rabbitmq`.
- `decimal` serializado com 2 casas (round HALF-UP).
- Validação de parâmetros de rota (inteiros positivos).

## 9. Infraestrutura e Docker

`docker-compose.yml` com três serviços em uma rede dedicada:

- `postgres`: imagem `postgres:16-alpine`, volume persistente, healthcheck `pg_isready`.
- `rabbitmq`: imagem `rabbitmq:3.13-management` (UI em http://localhost:15672,
  guest/guest), healthcheck `rabbitmq-diagnostics ping`.
- `api`: build do `Dockerfile` da solução, `depends_on` com `condition: service_healthy`,
  migrations aplicadas automaticamente ao iniciar (`EF Migrate` programático),
  porta 8080.

Variáveis de conexão via `appsettings.json` + environment variables
(`ConnectionStrings__Postgres`, `RabbitMQ__Host`, etc.). O `Dockerfile` deve ser
multi-stage (SDK para build, ASP.NET runtime para execução).

Incluir um utilitário para demonstração: script (`scripts/send-message.sh`) ou endpoint de
teste que publique a mensagem-exemplo na fila, permitindo validar o fluxo completo
(pub → consume → API).

## 10. Testes obrigatórios

- **Unitários (domínio)**: invariantes (quantidade/preco inválidos), consolidação de itens
  duplicados, cálculo de valor total.
- **Unitários (aplicação)**: handlers com repositórios falsos (NSubstitute/Moq), validação
  da mensagem, idempotência (pedido duplicado → não persiste de novo, faz ack).
- **Integração** (Testcontainers Postgres + RabbitMQ ou `WebApplicationFactory` com fakes):
  - Publicar mensagem-exemplo na fila → aguardar consumo → `GET /api/pedidos/1001/total`
    retorna 120.00.
  - Publicar duas vezes a mesma mensagem → contagem de pedidos do cliente permanece 1.
  - `GET /api/clientes/1/pedidos/quantidade` e `/pedidos` corretos.
  - 404 para pedido inexistente.
- Cobertura mínima de código no domínio: 80%.

## 12. Critérios de aceite (Definition of Done)

- [ ] `docker compose up -d` sobe tudo e a API responde `/health/ready` = healthy.
- [ ] Migrations criam o schema automaticamente.
- [ ] Publicar a mensagem-exemplo na `pedidos.queue` resulta em persistência correta
      (pedido, produto por nome, itens) em PostgreSQL.
- [ ] `GET /api/pedidos/1001/total` retorna 120.00 (100 × 1.10 + 10 × 1.00).
- [ ] Mensagem duplicada não gera pedido duplicado.
- [ ] Quantidade e lista por cliente retornam dados corretos.
- [ ] Mensagem inválida vai para DLQ sem travar o consumer.

- [ ] Camadas DDD e SOLID respeitadas (domínio sem dependências externas, DI no host).
- [ ] Swagger funcional e documentação completa.

## 13. Restrições e boas práticas

- Português nos nomes de negócio se desejar, mas código/identificadores em inglês.
- Nenhuma string de conexão/segredo hardcoded; usar user-secrets ou env vars.
- Transações com escopo curto; sem locks manuais.
- Erros nunca engolidos silenciosamente: sempre log estruturado com contexto
  (codigoPedido, deliveryTag).
- Não implementar autenticação (fora do escopo do desafio), mas deixar a arquitetura
  preparada para middleware.
